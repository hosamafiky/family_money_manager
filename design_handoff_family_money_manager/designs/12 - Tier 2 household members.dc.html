Six boards, section U. Read in full before drawing: household_member.dart, household_use_cases.dart, drift_household_repository.dart, household_members_screen.dart and every member* value in both ARB files. This is the smallest feature in Tier 2 and it produced the sharpest defect so far — archiving a member is not balance-guarded, while goals and certificates both refuse. READ FIRST

Four defects, and one of them is a disagreement between the UI and the database

DEFECT 1 · the money outlives the member

Archiving يوسف is allowed while 6,950.00 sits in his protected fund.

archiveMember checks exactly three things: the member exists, the member is not the primary user, and the member is not already archived. It never looks at owned or beneficiary accounts. So the child-protected fund — the one balance in this product that exists to protect somebody who cannot advocate for themselves — is left pointing at an archived beneficiary.

Both comparable features refuse. errorGoalArchiveNonzeroBalance: «لا يمكن أرشفة هدف يحتوي على أموال. حرِّر جميع الأموال أولاً.» errorCertificateArchiveNonzeroBalance: «لا يمكن أرشفة شهادة بها أصل متبقٍ. استردها أولاً.» Members have no equivalent, and a guarded withdrawal's acknowledgement checkbox names the child — so the name has to keep resolving.

This is domain work, not presentation. U4 draws the guard the redesign needs: a refusal with the balance stated and a route to empty the fund first. One new use-case check, one new key.

DEFECT 2 · the UI and the DB disagree about the spouse

Archive the spouse and «إضافة زوج/ة» never comes back — but the database would allow it.

The repository's uniqueness check counts active spouses only: role == spouse & isArchived == false. The screen computes hasSpouse from members.where(role == spouse) — archived included — and hides the add button whenever the list is non-empty.

So after an archive, the only affordance for adding a spouse is gone from a household the domain considers spouse-less. Nothing errors; the feature just quietly stops existing. One filter fixes it, and U5 draws the state that exposes it.

Related, same board: archiving is one-way. Goals have goalRestoreAction «استعادة», certificates have a restore use case — members have neither a use case nor a key. An archived member is archived forever.

DEFECT 3 · «مؤرشف» has one gender

archivedLabel is a single masculine string, and it is rendered under هناء exactly as it is rendered under يوسف. In an Arabic-first product that is not a nitpick — it is the label reading as ungrammatical about a named family member on her own row.

Same shape as memberChild «طفل», a singular used as the heading of a list that can hold several. Both need gender/number-aware forms; ARB supports select and plural, and neither is used here.

DEFECT 4 · rename is retroactive and silent

renameMember overwrites displayName in place — the only in-place mutation of user-visible data anywhere in this product. Because the transaction list joins member names rather than storing them, a rename changes how every past entry reads, including the audit trail on protected withdrawals.

That is the right behaviour — people's names change and the ledger should not fossilise a typo — but in an app whose first law is «مفيش تعديل», it has to be said out loud. U3 says it.

WHAT SOURCE GETS RIGHT

Three roles, two lifecycles, and no delete — consistent with the ledger. The primary user cannot be archived and cannot be added twice; household initialisation is idempotent on fixed ids. memberSpouseLoginNote already tells the truth about V1 rather than hiding it.

And there is deliberately no age, no date of birth, no relationship field. The redesign adds none: a protected fund's rules do not change on a birthday in V1, so a birthday would be a promise the product cannot keep.

Household members — six boards

The shipped screen is three _SectionHeaders in a ListView, a Card per member, a PopupMenuButton for rename and archive, and three AlertDialogs. It has no empty state (the primary user always exists), no skeleton, and no link between a member and the money attached to them — which is the gap that matters: يوسف has 6,950.00 in this app and his row does not know it.

This board draws a rule that is not in the code, and says so on its face. Today archiving يوسف succeeds — the use case checks the role and the lifecycle and nothing else — leaving 6,950.00 of protected money pointing at an archived beneficiary, on an account whose withdrawal flow requires an acknowledgement that names him. The comparison table is the argument: two features already refuse in exactly this situation and both have a shipped sentence for it. The refusal routes forward instead of dead-ending — the only legitimate path is to empty the fund through the guarded withdrawal, which is one tap away and still asks for a reason. No coloured frame and no heavy haptic: this is a refusal, not a consequential write, and the frame stays exclusive to the guarded withdrawal itself.

An archived member is history, not an absence. هناء's row stays, outlined rather than filled — the same treatment the accounts list gives an archived account — with «للقراءة» and one sentence confirming her past entries still read her name. Deleting the row would orphan every transaction that references her. «مؤرشفة» is the grammatical form archivedLabel cannot produce and is marked as proposed for that reason alone; the ARB needs a select on gender, or the label reads wrong about half the household. The red notice is unusual for this set — commentary normally lives in the note below the frame — but this one is depicting the *difference* between two behaviours in the same place, and the board is the only place both can be seen at once.
