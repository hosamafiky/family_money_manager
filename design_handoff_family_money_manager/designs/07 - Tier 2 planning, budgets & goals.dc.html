Two corrections that reach back into earlier deliverables

CORRECTION 1 · affects D2 §7.3 and Tier 1

Budget thresholds are 80% and 100%, fixed. There is no configurable alert level.

I drew a progress meter reading "تجاوزت حد التنبيه (90%)", implying a user-set threshold. BudgetUsageState defines five states with hard boundaries: noSpending 0%, onTrack <80%, nearLimit ≥80%, limitReached =100%, overBudget >100% — and computeUsageState hard-codes them.

All five already have ARB labels: «لا إنفاق» · «في المسار الصحيح» · «قرب الحد» · «تم الوصول للحد» · «تجاوز الميزانية». So the meter should name the state, which is better than a percentage anyway — it's the text half of "never colour alone", already localised.

Also: percentageUsed is integer division, truncated. 2,410 of 3,500 is 68%, not 69 — I had rounded. And it returns null when the limit is zero, which is a state the meter must render.

CORRECTION 2 · the source agrees with a decision you made

The ARB already says «إجمالي الأصول لا يزيد» — the same phrase you chose for the dashboard.

goalReserveDedicated reads, verbatim: «يُنشأ حساب احتياطي مخصص لهذا الهدف. التمويل تحويل داخلي — إجمالي الأصول لا يزيد.»

You renamed the dashboard strip from «صافي الثروة» to «إجمالي الأصول». The product's own goal copy was already using that exact term for the same reason — funding a goal moves money without creating any. That's a good sign the rename is right rather than a compromise, and it means the two screens now speak with one voice without either being changed to match.

goalReleaseTransferNote is equally direct — «هذا تحويل داخلي — وليس دخلاً» — so the transfer-is-not-income invariant already has localised copy in the goal flow. I've used both verbatim rather than writing my own.

K

Planning hub and budgets

A budget contains no money. budget.dart's own comment: "Does not contain money. Does not move money. Does not create accounts." So a budget never appears in the accounts list, never in the held region, and its consumption is a query over expenses — which is why budgetOverlapNote can say two budgets may overlap without double-counting anything.

L

Budget detail, and goals — lifecycle is not progress

The audit warned that goal lifecycle and derived progress get confused. The domain keeps them strictly separate and gives each its own labels: status is «نشط · تم بلوغ الهدف · مكتمل · مؤرشف», progress is «لم يبدأ · جارٍ · تم بلوغ الهدف · ممول بزيادة». A goal can be target reached in progress while still active in status — that is the case the design has to make obvious.

Two badges, two vocabularies, and now with the citation. goal.dart:18 is explicit: "only active, completed, and archived are persisted. Funding progress … is derived solely via GoalProgressState … never written to goals.status." So «الحالة: نشط» is correct for this fixture — a goal does not auto-transition when its target is passed — and «التقدّم: ممول بزيادة» is the derived value, since fromBalance(13600, 13000) returns overfunded. Status is caller-set through a lifecycle event; progress is a pure function of balance vs target. The amber notice is the rule in one sentence. That is the audit's lifecycle-vs-progress confusion answered by showing both rather than picking one. Overfunding draws exactly like over-budget: ink consumption to 100%, then a hatched overshoot band — same component, same rule, only the hatch takes goalReserved here where the budget takes expense. Consumption is always ink; the hatch carries the signal.

Both footnotes resolved by reading goal.dart

«مكتمل» is a user action, confirmed — and heavier than I drew it. GoalLifecycleEvent carries completionType 'normal' or 'early', with earlyCompletionReason required and earlyCompletionConfirmed forced true when early. That makes early completion the fourth flow demanding a written justification, alongside protected withdrawal, reversal and goal release. It needs the GuardedConfirmSheet treatment, not a plain dialog — I'll draw it with the goals list next turn.

GoalPurpose has 7 values: emergencyFund · homePurchase · education · travel · majorPurchase · familyEvent · other — and like FundPurpose, no localization exists for them. Add 7 more keys × 2 locales and a third helper function to D6 §05's count.

Finding — an orphaned ARB key. goalStatusTargetReached «تم بلوغ الهدف» exists in the ARB but GoalStatus has no targetReached member; the doc comment marks that as a Phase 5B.8 removal. The key is dead and duplicates goalProgressTargetReached. It very nearly made me draw the wrong badge — worth deleting so it can't mislead again.

Also from the read, applied: remainingMinorUnits is clamped to zero above target, so an overfunded goal shows «المتبقي 0.00» and the surplus only in overfundedMinorUnits — never a negative remaining. That is the opposite of the budget meter, where remaining does go negative.
