Family Money Manager · D3 · Tier 1 · turn 2 of 3

Transaction list, detail,
and the reversal

Ten artboards (C1–C6, D1–D3b). The list against 1,248 real transactions with filtering and search; the detail showing its actual double-entry rows; and the append-only correction — the one moment in the product where the UI has to teach the data model rather than hide it.

C

Transaction list

What it solves. Audit problems 4 and 7 — one row model, direction never by colour alone, no reinvented amount rows. Built for 400+ transactions: fixed-geometry rows for virtualisation, sticky date group headers, and a period summary that never sums across currencies.

The row is 64 dp minimum and intrinsic above it. Leading edge (solid income / solid expense / dashed transfer / grey reversed) → title → meta line → amount. Four channels per row, same grammar as the dashboard.

The bidi case that breaks naive implementations. The query «بقالة 382» is RTL text containing an LTR numeric run; the field, the highlight spans and the caret all have to survive it. Each numeric run — in the field, in the amounts, in the note quote, in the saved-search chips — is a first-strong isolate. Search deliberately ignores the active period, and says so with a one-tap way to re-apply it, because a user searching for an amount is looking for a specific transaction, not browsing a month.

D

Transaction detail and the append-only correction

What it solves. The hardest teaching problem in the product. There is no edit and no delete anywhere on these screens — and rather than hiding that, the detail shows the transaction's real double-entry rows and, when reversed, both halves of the lineage. The user learns the ledger by reading his own transaction.

Correction to last turn, and what's actually missing

I claimed the reversal needed two, then three, new fields. Having now read the tables: nearly all of it already exists.

Existsoperations.isReversed — operations_table.dart:87. A list row renders "معكوسة" from the row it already has. No second query, no new field. Existsoperations.reversedBy — :90. The forward link I asked for is already there, and the table comment names isReversed and reversedBy as the only two mutable columns. Existsledger_entries.isReversal + reversalOfEntryId — ledger_entries_table.dart:53,56. The entry-level back link for D2's chain. Existsoperations.createdBy — so D2's "بواسطة أحمد" reads off the reversal operation. No reversed_by_member_id needed; I withdraw it. MissingA dedicated reversal reason. operations.description exists and could hold it, but then a reason is indistinguishable from an ordinary description — and D3 prints it as an audit field. This is the one real gap: either accept description as the store, or add reversal_reason on the reversal row (a new row, so the immutability rule on the original is untouched).
Genuine assumptions left in these ten boards
  1. C1's meta line needs name lookups. TransactionSummary carries spenderMemberId and the operation's sourceAccountId — ids, not names. Rendering "هناء · محفظة نقدية" needs member and account maps joined into the list provider. Real work, and it is the difference between my row and a buildable one.
  2. The four suggested reversal reasons are localised presets needing ARB entries, not free text.
  3. Budget impact on the detail screen, and budget restoration shown in D3, both need a budget read during a transaction render — a provider dependency the detail screen doesn't have today.
  4. Search covers description, notes, amount and account name. Notes are searched — confirm that's acceptable if notes are ever sensitive.
  5. "تكرار" prefills a new entry and does not clone an id; idempotency stays in record_expense_use_case.
