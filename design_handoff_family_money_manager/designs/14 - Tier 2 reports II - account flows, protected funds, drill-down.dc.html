One gift in the domain, one UUID on the most sensitive screen

THE GIFT · AccountFlowBreakdown.reconciles

The accounting identity is already computed. Nothing displays it.

The model documents it as a RECONCILIATION INVARIANT: opening + income − expense + transfers in − transfers out + adjustments + reversal effect = closing, and exposes bool get reconciles which checks exactly that. reconciles is called nowhere in the presentation layer.

Worse, the card omits any row whose value is zero (if (… != 0)), so the column the user sees does not add up even when the arithmetic does — an opening balance, three of seven possible middle rows, and a closing balance.

This is the report that proves the product's first claim — «الرصيد محسوب من القيود، مش رقم مخزّن». Y1 prints all seven rows including the zeros, then prints the check.

DEFECT · a UUID where a child's name belongs

The protected-funds audit row prints audit.beneficiaryMemberId raw.

_AuditRow's subtitle is '${l10n.reportBeneficiary}: ${audit.beneficiaryMemberId}' — so the screen reads «المستفيد: 3f9a…-b21c». WithdrawalAuditSummary carries the id and no name, which makes this handoff §9's ids-not-names gap, live, on the one screen whose entire purpose is accountability.

The guarded withdrawal makes the user tick a box that names the child. The audit trail that records it cannot say the name back. One join on the query, and the report becomes readable by the person it protects.

Second issue on the same card: two bold totals — «الرصيد الختامي للفترة» and «الرصيد الحالي» — printed adjacently with nothing explaining that one is period-bounded and the other is live.

A COLOUR THAT IS NOT IN THE SYSTEM

Colors.blue marks transfers in both the account-flow card and the drill-down list. AppFinancialColors has no blue — transfer is #605D5D, achromatic on purpose, because a transfer changes no total.

The drill-down's _color() also sends childFundWithdrawal to plain red and everything unrecognised to grey, so a protected withdrawal is indistinguishable from an ordinary expense — while row.isProtectedWithdrawal sits on the model, unused.

TWO STRINGS ASSEMBLED IN CODE

The account-flow card builds its transfer labels as '${transactionTypeTransfer} (+)' and '… (-)'. A parenthesised ASCII sign glued onto a translated noun is not translatable, and in RTL the parenthesis pair reorders around the sign.

It also reuses dashboardPeriodIncome / dashboardPeriodExpenses as row labels — dashboard keys on a report card. Four proposed keys replace all of it: transfers in, transfers out, and the two flow labels.

THE DRILL-DOWN IS REACHABLE, BUT NOT FROM A REPORT

The list itself is fine: every row taps through to /transactions/:operationId, and it reads the same reportRequestProvider. So it inherits the period — but since no report row sets a filter, opening it always yields everything in the period.

It also has no date grouping and no sticky headers, unlike 04 · C1's transaction list. Two lists of the same rows, two layouts. Z2 uses the C1 pattern.

Two things the shipped report cannot express, on one board. First, a period with no activity: source omits every zero row, so a dormant account renders as two identical numbers with nothing between them and looks like a bug. Naming the empty middle as «كل الحركات 0.00» costs one row and removes the ambiguity. Second, a failed identity. reconciles returning false cannot be the user's fault — every input is derived from the ledger — so the copy says so in the first clause and points at the authoritative screen. This board is a diagnostic state, not fixture data: the 250.00 gap is deliberately synthetic, which is why the section heading says so and the wallet's figures appear nowhere else in the set.

Zeros do not mask. 0.00 is not a secret and barring it would imply a hidden figure where there is none — the same rule 11 · M6 applied to an empty goal, inverted: there, a lone printed 0.00 would have identified which goal was empty; here every account shows its zeros, so no one row is singled out. A protected withdrawal must not look like an expense, and in source it does. _color() maps childFundWithdrawal to the same red as expense, and row.isProtectedWithdrawal — a boolean that exists precisely to prevent this — is never read. The redesign gives the row the hatched edge with a 2 px protectedMoney frame, the lock, the beneficiary and the reason, which is the same treatment the accounts list gives the fund itself. And the empty state finally distinguishes its two causes. With a filter applied, «لا توجد بيانات لهذه الفترة.» is misleading: there is data, the filter excluded it. Both exits are offered — drop the filter, or move the period — because the user's intent could be either.

String provenance — closed rule

From ARBEvery unmarked Arabic string: «تدفقات الحسابات» «الأموال المحمية» «عرض المعاملات» «الرصيد الافتتاحي» «الرصيد الختامي» «الرصيد الختامي للفترة» «الرصيد الحالي» «موّل» «السحوبات» «أثر العكس» «الإجماليات مفصّلة بالعملة» · the period chips «هذا الشهر» «الشهر الماضي» «هذا العام» «مخصص» · «{count} معاملات» · «لا توجد بيانات لهذه الفترة.» · «المستفيد» from reportBeneficiary, where a trailing ◂ marks only the proposed remainder of its line · and the five scope* labels where they appear as meta («المنزل»). Mine · marked ◂The mark is exhaustive. Every Arabic string in a frame that is not a verbatim ARB value carries ◂ — «دخل» / «مصروف» / «تحويلات داخلة» / «تحويلات خارجة» / «تسويات» as flow-row labels (source reuses dashboard keys and glues «(+)» onto them), the reconciliation lines, «حالة تشخيصية», the filter chips, the day headers, every account and category name, «عرض التدقيق الكامل», and all explanatory Egyptian sentences. If a framed string has no ◂ and is not in the first bucket, that is a defect in this document. Not copy, so unmarked: fixture data — member, account and category names, user-entered text such as the withdrawal reason «رسوم مدرسة» carried from 05 · G2, amounts, dates, counts — and the English annotation outside the frames.
